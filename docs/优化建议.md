## 总体评价

项目底子相当好，以下优点应保持：

- **架构分层清晰**：constants ← board ← rules ← state ← ai ← main，ui 只依赖 constants/board，无循环依赖；状态唯一真源在 state.js。
- **AI 基础设施完备**：迭代加深 + aspiration window、killer moves、MVV-LVA 走法排序、quiescence + delta 剪枝、make/unmake 原位搜索，已好于一般业余水准。
- **注释质量高**：大量"踩坑记录 + 回退原因"（如鞅设计回退、flipCollapse 回退）写进了代码注释，非常有价值。
- **签名密码管理正确**：keystore.properties 正确 gitignore，git 历史确认从未泄漏。
- **Electron 安全基线达标**：nodeIntegration off / contextIsolation on / 无 preload / window.open 全 deny。
- **有 65 个单元测试用例**（node:test 零依赖）且全部通过，有版本一致性专项测试。
- **UI 细节到位**：`prefers-reduced-motion` 全覆盖、色弱友好形状区分、aria-label 不泄露暗子信息、Worker 不可用双路降级、`100vh/100dvh` 双写。

主要问题集中在四块：**① 几个真实的正确性缺陷（worker 僵尸 / 迟到结果污染）、② 仓库卫生严重失控（38MB APK 入库、.git 膨胀到 146MB）、③ AI 热路径存在大量可零风险消除的内存分配与重复计算、④ 缺少对局存档与 CI**。

## 一、正确性缺陷（P0，建议立即修）

### P0-1 Worker 僵尸化 + 迟到结果污染（已复核确认）

**位置**：`js/main.js:200-203`（watchdog）、`main.js:232-237`（onWorkerError）、`main.js:63`（reset）

**问题**：三个缺陷复合成一条真实的错误链路——

1. watchdog 触发时只 `aiWorker = null`，**从不调用 `terminate()`**：旧 worker 线程继续满负荷跑完 4.5s 搜索预算（移动端耗电/发热）；下次 `ensureWorker()` 又建新实例，**双 worker 并存抢 CPU**，低端机越卡越慢、越慢越触发 watchdog，恶性循环。
2. watchdog 走 `runAISync()` 同步补走这步，但 **`thinkId` 未自增**：慢 worker（只是慢不是死）稍后回传的结果仍能通过 `msg.id !== thinkId` 检查（main.js:224）→ 对已经易主的局面调 `STATE.applyMove`。轮次校验会拒绝它（状态不坏），**但返回值没人检查**（见 P0-2）→ `soundAfterApply()` 照常执行 → **重播上一步音效、"司令阵亡，军旗显形" toast 二次弹出**。
3. `reset()` 重开新局只自增 thinkId 丢弃结果，旧 worker 同样跑满预算不 terminate。

**修复**（几行）：

```js
function killWorker() {
  if (thinkWatchdog) { clearTimeout(thinkWatchdog); thinkWatchdog = 0; }
  if (aiWorker) { aiWorker.terminate(); aiWorker = null; }
}
// watchdog 回调：thinkId++; killWorker(); runAISync();
// onWorkerError：thinkId++; killWorker(); runAISync();
// reset()：killWorker();
```

worker 重建成本极低（importScripts 5 个小文件），terminate 是取消同步计算 worker 的唯一可靠机制。

### P0-2 applyMove 返回值被忽略

**位置**：`js/main.js:216`（runAISync）、`main.js:228`（onWorkerResult）

**问题**：两处都不检查 `STATE.applyMove` 的布尔返回，失败时仍执行 `soundAfterApply()`。与 P0-1 复合后就是"错音 + 双 toast"的直接来源；单独看也是一条静默吞错的路径。

**修复**：统一改 `if (!STATE.applyMove(state, action)) { console.warn('[main] applyMove rejected', action); return; }`。

### P0-3 终局弹层定时器闭包捕获旧 state

**位置**：`js/ui.js:509-511`

**问题**：`setTimeout(() => { if (state.winner) go.classList.remove('hidden') ... }, 700)` 里的 `state` 是本次 render 的**实参引用**（旧局对象，winner 永真）。终局后 700ms 内连点两次顶栏"重新开局"（armed 双击机制允许）→ 新局已开始，旧定时器仍把结算浮层弹在新棋盘上。对照 `main.js:175-180` 的音效定时器读模块级 `let state`，处理是正确的。

**修复**：定时器内比对 `state === Junqi.main.getState()` 再弹层；或引入自增 gameId。

### P0-4 worker 回传 null action → AI 永久停摆

**位置**：`js/main.js:227` + `js/ai.js:996-998`

**问题**：`if (!msg.action) return;` 之后没有任何重调度。而 `chooseHard` 的 catch 块**静默吞掉所有非预算异常**回退 medium，`ai.js:997` 的"理论不可达"分支恰好会返回 null——一旦触发，游戏卡死且无任何日志，线上表现为"AI 突然变笨/不动了"，极难排查。

**修复**：① `if (!msg.action) { runAISync(); return; }` 兜底；② ai.js catch 中加 `console.error('[ai] search failed, fallback to medium', e)`，并让 worker 在 result 消息里带 `degraded: true`。

### P0-5 make-icons.sh 静默用旧图标覆盖新 logo

**位置**：`scripts/make-icons.sh:17`

**问题**：`cp desktop/icon.png assets/logo.png`——desktop/icon.png 是旧的 512×512 图标，assets/logo.png 是 v1.0.10 起用的 1024×1024 国潮印章新图标。现在谁跑这个脚本，就会**用旧图标覆盖新 logo 并生成全套旧图标资源**，无任何警告。

**修复**：明确唯一图标源为 `assets/logo.png`，删掉这行 cp 或反转方向；脚本开头加存在性检查。

### P0-6 取消静音后可能永久无声

**位置**：`js/sfx.js:172-177, 194-199`

**问题**：`play()` 中 `if (muted) return;` 在 `ensureCtx()` **之前**。用户全程静音 → AudioContext 从未创建；之后在 click 里取消静音，紧接着的第一个音效若是 **AI 落子音**（450ms setTimeout + worker 回调，非用户手势栈）→ 此时才 `new AudioContext()`，Android WebView/iOS 自动播放策略下创建即 suspended，非手势中 `resume()` 可能无效 → 取消静音后一段时间无声。

**修复**：`toggleMuted()`（必在 click 手势内被调）取消静音时顺手 `ensureCtx()` 预热，或播一个 0 增益静音 buffer 完成解锁。顺带：`sfx.js:18` 的 `ctx.resume()` 加 `.catch(()=>{})` 消 unhandledrejection 噪音；可监听 `statechange` 在 iOS `interrupted`（来电）后主动 resume。

## 二、仓库卫生与版本管理（REPO）

### REPO-1 九个 APK（约 38MB）被 git 跟踪，且在"制度化"增重 【高】

**位置**：仓库根目录 `军旗翻翻棋-v1.0.5.apk` ~ `v1.1.0` 等 9 个文件（已用 `git ls-files` 复核确认）

**问题**：根 `.gitignore` 没有 `*.apk` 规则（android/.gitignore 的只管子目录）。更糟的是有制度化趋势：`dist-desktop.sh` 打完 APK 自动归档到仓库根目录（commit d777f80 专门加的），`update_normal.sh` 又是 `git add -A` 全量提交 → **每次发版仓库永久增重 3.5~7MB**。远端是公开 GitHub 仓库，每次 clone 都拉全部历史 APK。

**修复**：
1. `git rm --cached *.apk`；
2. 根 `.gitignore` 追加 `*.apk`；
3. APK 分发改走 GitHub Releases（`gh release create v1.1.0 *.apk`）；dist-desktop.sh 的归档目标改为已 gitignore 的 `dist/` 或 `releases/`。

### REPO-2 .git 达 146MB：历史中残留 dist/ 桌面构建产物 【高】

**问题**（已复核 `du -sh .git` = 146M）：历史 blob 榜几乎全是 `dist/军旗翻翻棋-win32-x64/` 下的文件——app.asar 多个历史版本（52/21/18/14/11/7MB）、dxcompiler.dll 25MB、LICENSES.chromium.html 20MB 等。f1059f5 "dist/ 移出 git 跟踪"只做了 `git rm --cached`，**没有重写历史**。源码不到 1MB 的项目背着 146MB 的 .git。

**修复**：`git filter-repo --path dist --path-glob '*.apk' --invert-paths` 后 force push；或鉴于 52 个 commit 中 28 个 message 是 "u"、历史价值很低，直接以当前工作树重建仓库（squash 成一个初始 commit）。重写前通知协作者（如有）。完成后 .git 应回到几 MB。

### REPO-3 update_normal.sh：`git add -A` + 默认提交信息 "u" + 自动 push 【中】

**问题**：无差别暂存一切（APK 入库的直接根因）；52 个提交 28 个叫 "u"；一旦哪天把敏感文件（临时拷入的 keystore、密码文件）放进工作区，会被一条命令直接推上**公开**仓库——这是签名安全唯一真正的"一键翻车"路径。

**修复**：① 提交前打印 `git status --short` 并要求确认；② 去掉默认 "u"，强制填 message；③ `git add -A` 改 `git add -u` + 显式添加新文件。

### REPO-4 版本号 4 处手工维护，测试只覆盖 1 处 【中】

**位置**：package.json（1.1.0）、js/constants.js（VERSION）、index.html:16（硬编码 `v1.1.0` span）、android/app/build.gradle（versionName/versionCode 9）。tests/version.test.js 只校验 constants↔package.json。目前四处恰好一致，但 build.gradle 与 index.html 完全靠人肉。

**修复**：扩展 version.test.js 读 build.gradle 文本断言 versionName == pkg.version、读 index.html 断言 span 版本；进一步可在 dist-desktop.sh 的 android 分支用 sed 自动写入 versionName 并自增 versionCode。

### REPO-5 package.json `dist:win` 与 dist-desktop.sh 双份维护 【中】

**问题**：`--app-version=1.1.0` 写死（脚本是动态读的），下次升版本必然漂移；149 字符的白名单 ignore 正则在两处各存一份，改一处忘一处就会把垃圾打进 asar。

**修复**：`"dist:win": "scripts/dist-desktop.sh win"`，删除 package.json 里的整条重复命令，正则只留脚本一处。

### REPO-6 杂项清理 【低】

- `assets/logo_v3.png` 与 `logo.png` **MD5 完全相同**且全仓库零引用 → 删除；`logo.png` 用 pngquant/oxipng 压缩（1.6MB → 几百 KB）。

## 五、AI 引擎优化（AI）

> 总评：引擎**不缺基础设施**（迭代加深/aspiration/killer/quiescence/make-unmake 全有），最大的问题在 **(a) 热路径海量小对象分配与字符串操作、(b) flip chance 节点组合爆炸无约减、(c) worker 工程缺陷（已列 P0-1）**。5.A 全部是"零行为变化"的纯性能重构，可用现有 boardSig 快照测试 + benchmark prev 模式（同种子应逐局结果完全相同）验证；5.B 是有损/近似改动，必须走完整 A/B + 真人体验验收（项目有"自弈 A/B 不差但真人体验为负"的历史教训，见 ai.js:259-267 注释）。

### 5.A 零风险纯性能包（按投入产出排序）

#### AI-1 evaluateBase 的 EV 循环写在逐格循环内部 【高，一行级修复，全引擎单点最大纯浪费】

**位置**：`js/ai.js:315-322`（已复核确认）

`for (const key in rem)` 的 24 键 EV 循环在**逐格循环内部**，但 ev 与格子无关：30 个暗子 × 24 键 = 每次 evaluate 约 720 次 `key.split(':')`（每次分配 2 个字符串）+ 720 次哈希查找。evaluate 是叶子/quiesce 每节点必调。

**修复**：EV 移出逐格循环算一次，`score += ev * 0.5 * totalUnrevealed`（数学恒等）；同时模块加载时预计算 `REM_KEYS`（24 个 [type, side, value] 三元组），消灭 split。预期 evaluate 成本降 ~50%+，零行为变化。

### 5.B 算法性改进（须 benchmark + 真人体验双验收）

#### AI-10 flip chance 节点组合爆炸，无等价类约减 【高，全局最大算法提速点】

**位置**：`js/ai.js:726, 788-836`

每个内部节点把全部暗子格（开局 45+ 个）作为独立 flip 动作展开，每个 flip 又是 K 路（hard=3/master=5）chance 采样 × 全窗口子树。开局根节点成本 ≈ 45 flip × K 采样 × 无剪枝子树，hard 档（nodes=6000）开局实际只能完成 1-3 层迭代——**深度预算几乎全被"翻哪一格"吃掉**。而所有 flip 的 chance 分布完全相同（同一 rem 分布），差异仅在格子位置属性。

**建议**：根节点保留全部 flip；**内部节点将 flip 按（terrain, 邻接己方大子数, 是否 gate 相邻）分等价类，每类取 1 个代表**。预期同预算下迭代深度 +2~4 层。

#### AI-11 嵌套 chance 静态化 【高】

**位置**：`js/ai.js:819-820, 268-269`

`inChance=true` 子树强制全窗口且叶子禁 quiesce（注释自认"成本爆炸"），更糟的是 chance 子树内的节点仍含 flip 动作 → **嵌套 chance 采样**，成本按 K^层数 增长。`flipCollapse` 机制已实现但两个预置都是 false（历史 A/B 回退）。

**建议**：做与当年"按绝对深度 collapse"不同的**定向变体**：仅当 `inChance === true` 时对 flip 用已有的 `flipOptionValue` 静态近似，杜绝嵌套 chance；根层与第一层 chance 展开保持精确。这与 v1.0.6 回退的全局 flipCollapse 不是同一东西，值得用 cfg 开关重测。

#### AI-12 checkWinner 惰性化 【中高，残局搜索大头】

**位置**：`js/ai.js:495, 520, 561, 579, 817` → `js/rules.js:171-180`

每次 applyAction 和每个 chance 采样都全量跑 checkWinner → hasAnyLegalMove。中局有暗子时廉价短路（rules.js:137-139），但**暗子翻完后的残局每个节点都要对全部子力完整生成 legalMoves（含工兵 BFS）只为判非空**——恰好是搜索最深、节点最多的阶段。

**修复**：① rules.js 增加无分配的 `hasLegalMoveFrom(state, i)`（找到第一个合法落点即 return true）；② 搜索内部只在"上一步是吃子/翻子或 staleCount 逼近上限"时查 winner，quiet 走子不可能新产生"无子可动"，可安全跳过。

#### AI-13 quiesce 专用 legalCaptures 【中】

**位置**：`js/ai.js:624-643`

captureActions 对每个己方已翻子调完整 `R.legalMoves`（含铁路扫描/工兵 BFS、生成全部安静走法对象），然后 `if (!t.piece) continue` 丢掉大部分。

**修复**：rules.js 增加 `legalCaptures(state, i)`：只扫 orth/diag 邻居中的已翻敌子 + 铁路方向只沿直线找**第一个**占用格，跳过空格落点生成；quiesce 专用，不碰 legalMoves 公共语义。

#### AI-14 可选增强（做完上面仍有预算富余再考虑）

- **置换表（TT）**：注意本游戏是暗棋 belief-state 搜索，TT 只对 move-only 子树（inChance=false，恰是剪枝生效节点最密处）有效；key 需含每格编码 + turn + staleCount（评估含 staleDecay 必须入 key）+ minesLost。60 格可用 `Uint8Array(60)` + 预计算随机表做增量 Zobrist（applyAction/undoAction 同步 xor），Int32Array 开放寻址。**优先级低于 flip 约减**。
- **根节点 PVS / 深层 LMR**：现有 ID+aspiration 已规范；LMR 属有损剪枝，须过 benchmark + 真人体验双关。

### CORE-1 三套平行"走子应用"实现 【高，本次审查最大的维护性问题】

### UI-1 每次点按全量重建棋子层 【中】

**位置**：`js/ui.js:262-285` + `main.js:100/110/114/119/136`

## 八、功能缺失（FEAT）

### FEAT-1 对局存档/恢复 【高（功能缺失）】

**问题**：刷新页面、误关窗口、手机端切后台被杀，对局即丢失。全项目唯一持久化是音效静音开关（sfx.js:14,196）。而**基础设施已经齐备**：state 被刻意保持纯数据可序列化（main.js:22 注释）、snapshot() 已存在、worker 协议本身就是"序列化 state → 计算 → 回传 action"。

**落地方案**：
1. onChange 回调里 debounce（~500ms）写 `localStorage['junqi-save-v1']`：`{ version: C.VERSION, mode, difficulty, state: snapshot(state) }`；
2. 启动时读档并跑 `validateSave()`：version 匹配、board.length===60、每类子在场数+captured 计数 ≤ PIECES[type].count、minesLost ∈ [0,3]、turn/controllers/winner 枚举合法——不合法静默丢弃回新开局（**同时封死 CORE-6 的 turn=null 与 CORE-2 的 minesLost 缺失这两个坏状态攻击面**）；
3. 恢复后重挂 state.onChange（JSON 往返已丢掉它，属既有行为）并重放 UI.render；
4. start 流程加"继续上局 / 新对局"选择；reset() 时清除存档；difficulty/mode 一并持久化（现在每次加载都回落 main.js:16 的 MASTER 默认值，用户选择丢失）；
5. 与 UI-2 的 Android 返回键处理联动（返回时若有未完结对局提示"进度已保存"）。

## 十、基准测试方法论（BENCH）

### BENCH-1 验收无统计显著性检验 【中】

**位置**：`scripts/ai_benchmark.js:157-185`

N=30-60 局下胜率阈值 0.50/0.55 的二项噪声约 ±9-13%（1σ）：真实胜率 0.52 的改动约四成概率"PASS"，0.48 的退化也有三成概率蒙混过关。项目历史上已因自弈噪声回退过多个特性（ai.js:259-267 注释），说明团队意识到了问题但工具没跟上。

**修复**：① 汇总行输出 Wilson score 置信区间（10 行代码）；② pass 条件改"CI 下界 ≥ minWR 或点估计 ≥ minWR 且 N ≥ 阈值"；③ 更优：SPRT 序贯检验（达到显著即停，省机时）；④ 关键决策用相同种子集配对 + McNemar 检验。

### BENCH-2 400 ply 截断局从胜率分母剔除 【低】

截断局往往正是"拖和/蹲营"风格对局，剔除会系统性高估进攻型引擎胜率（而"蹲营和棋体验为负"恰是本项目踩过的坑）→ capped 局按当前子力评估判代理胜者，或汇总单列 capped 局的引擎归属分布。

### BENCH-3 只测墙钟时间，无 nps 指标 【中】

5.A 分配优化的收益在"每步 ms"里被时间预算掩盖（time=800ms 打满时 ms 不变，变的是同预算内搜到的深度）。当前 depthA/depthB 是好代理，但缺节点数无法区分"搜得深因为 nps 高"还是"剪枝好"。→ ai.js 导出 `nodesSearched()`（配合 AI-9 的计数规范化），汇总行加 `nps` 与 `节点效率 = 完成深度/千节点`，性能重构前后各跑一次量化验证。

### BENCH-4 ab_test.js 默认 N=8 【低】

8 局的 A/B 在任何胜率差下都几乎不可能显著（0.6 真实胜率差也常判"无显著差异"），而输出文案会直接给"正收益，保留"结论，容易误导决策 → 默认 N ≥30 并带 CI，或结论行显式标注"样本不足，仅供参考"。
